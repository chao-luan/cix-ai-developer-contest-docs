# BIOS Flashing and Recovery

本文档用于在 BIOS 需要刷写、升级、重刷、回退或故障恢复时，通过 U 盘更新 BIOS 固件。

正常参赛流程下，选手收到的设备已经完成 BIOS 刷写和统一系统镜像预装，无需执行本章节操作。除非维护人员明确要求，或确认为 BIOS 故障恢复场景，否则不要自行刷写 BIOS。

```{danger}
严禁随意刷写 BIOS。

不同品牌、不同型号、不同硬件版本的开发板所使用的 BIOS 固件并不相同。例如 O6、O6N、MS-R1、EVB 等平台可能对应完全不同的 BIOS 文件。

刷写前必须确认开发板型号、硬件版本、Release 基线以及 BIOS 固件文件完全匹配。

如果刷入错误 BIOS，设备可能无法启动，开发者通常无法自行恢复，需要使用专用烧录工具或由维护人员进行救砖处理，恢复过程较麻烦且存在风险。

正常参赛流程下，设备出厂或发放前已经完成 BIOS 刷写。除非维护人员明确要求，否则不要自行刷写 BIOS。
```

## 1. BIOS 更新、升级和刷写的区别

“BIOS 更新”或“BIOS 升级”通常指将 BIOS 从旧版本升级到新版本，例如从 2026Q1 基线升级到 2026Q2 基线。

“BIOS 刷写”的范围更广，包括：

* 旧版本升级到新版本。
* 新版本回退到旧版本。
* 同版本重新刷写。
* 故障状态下重新恢复 BIOS。
* 工作人员批量制备设备。

本文统一使用“BIOS 刷写”描述该类操作。

## 2. 适用场景

仅在以下场景考虑 BIOS 刷写：

* 维护人员明确要求更新 BIOS。
* 当前 BIOS 版本与指定 Release 基线不匹配。
* 设备无法启动，且已排除电源、显示器、启动盘和 OS 镜像问题。
* 当前问题已确认与 BIOS 固件相关。
* 工作人员需要批量制备开发板。
* 需要将设备恢复到统一参赛环境。

以下场景通常不应直接刷 BIOS：

* Wi-Fi 异常。
* 图形界面黑屏但系统可以通过 SSH 登录。
* AI Demo 启动失败。
* SDK 包安装失败。
* Python 依赖异常。
* 端口占用。
* 单个应用无法运行。

上述问题应优先参考 [Troubleshooting](troubleshooting.md)。

## 3. 前置准备

准备以下硬件：

* 待刷写的开发板。
* FAT32 格式 U 盘。
* 显示器。
* HDMI / DP 线。
* 键盘。
* 稳定电源适配器。

准备以下文件：

```text
FlashUpdate.efi
<BIOS_FIRMWARE_FILE>.bin
```

示例：

```text
FlashUpdate.efi
cix_flash_all_rsa_pr.bin
```

```{warning}
BIOS 固件文件名仅作示例，实际文件必须以维护人员提供的版本为准。
```

## 4. 确认硬件型号和 BIOS 文件

刷写前必须确认以下信息：

| 检查项        | 说明                            |
| ---------- | ----------------------------- |
| 开发板品牌      | 例如 O6、O6N、MS-R1、EVB 等         |
| 硬件版本       | 不同硬件版本可能对应不同 BIOS             |
| Release 基线 | 例如 2026Q2 Release             |
| BIOS 文件名   | 确认是否为当前开发板对应固件                |
| 固件类型       | 注意 `_pr.bin`、`_proto.bin` 等差异 |
| 维护人员确认     | 高风险操作建议先确认后执行                 |

```{danger}
不要根据文件名猜测 BIOS 是否可用。不同品牌开发板的 BIOS 不能混刷，不同硬件版本也可能不能混刷。

如果无法确认 BIOS 文件是否匹配当前设备，请停止操作并联系官方人员。
```

## 5. 制作 BIOS 更新 U 盘

1. 准备一个 U 盘。
2. 将 U 盘格式化为 FAT32。
3. 将 BIOS 更新工具和 BIOS 固件文件复制到 U 盘根目录。

U 盘根目录应类似：

```text
FlashUpdate.efi
<BIOS_FIRMWARE_FILE>.bin
```

不要放在子目录中。

## 6. 进入 UEFI Shell

1. 将 U 盘插入开发板。
2. 接好显示器、键盘和电源。
3. 给设备上电。
4. 启动过程中连续按 `Esc` 进入 UEFI 设置界面。
5. 进入 `Boot Manager`。
6. 选择 `UEFI Shell`。

进入 UEFI Shell 后，屏幕会显示设备映射表，例如：

```text
FS0:
FS1:
FS2:
```

其中带有 USB 标识的条目通常为当前 U 盘。

## 7. 定位 U 盘目录

在 Shell 提示符下输入对应设备名，例如：

```text
FS1:
```

然后执行：

```text
ls
```

确认可以看到以下文件：

```text
FlashUpdate.efi
<BIOS_FIRMWARE_FILE>.bin
```

如果没有看到文件，可能是：

* 进入了错误的 FS 分区。
* U 盘不是 FAT32 格式。
* 文件没有放在 U 盘根目录。
* 文件名与实际命令不一致。
* U 盘未被 UEFI 正确识别。

可以尝试切换其他 FS 设备：

```text
FS0:
ls
FS2:
ls
```

## 8. 执行 BIOS 刷写

确认文件存在后，执行：

```text
FlashUpdate.efi -f <BIOS_FIRMWARE_FILE>.bin
```

示例：

```text
FlashUpdate.efi -f cix_flash_all_rsa_pr.bin
```

等待刷写完成。刷写过程中不要断电，不要拔 U 盘，不要重启设备。

```{danger}
BIOS 刷写过程中断电或刷入错误固件，都可能导致设备无法启动。
```

## 9. 重启设备

看到刷写成功提示后：

1. 关闭设备电源。
2. 等待数秒。
3. 拔出 U 盘。
4. 重新上电启动。
5. 观察是否可以进入系统。

## 10. 验证结果

确认以下项目：

* 设备可以正常上电。
* 显示器有输出。
* 可以进入 UEFI 设置界面。
* 可以识别启动盘。
* 可以进入操作系统。
* 系统版本与 Release 基线匹配。

进入系统后可执行：

```bash
uname -a
cat /etc/os-release
```

如有 BIOS 版本查询工具，可进一步确认 BIOS 版本是否符合要求。

## 11. 常见问题

### 11.1 UEFI Shell 中找不到 U 盘

检查：

* U 盘是否格式化为 FAT32。
* BIOS 文件是否放在 U 盘根目录。
* 是否更换 USB 接口。
* 是否更换 U 盘。
* 是否重新进入 UEFI Shell。

### 11.2 执行命令提示找不到文件

先执行：

```text
ls
```

确认文件名完全一致，包括大小写和后缀名。

例如实际文件名是：

```text
cix_flash_all_rsa_pr2.bin
```

命令中就必须写完整：

```text
FlashUpdate.efi -f cix_flash_all_rsa_pr2.bin
```

### 11.3 刷写后无法启动

可能原因：

* BIOS 固件与开发板型号不匹配。
* BIOS 固件与硬件版本不匹配。
* BIOS 固件与 OS Release 基线不匹配。
* 刷写过程中异常断电。
* 启动盘或 OS 镜像本身异常。

处理建议：

1. 断电后重新上电。
2. 检查是否可以进入 UEFI。
3. 检查 NVMe SSD 是否安装到位。
4. 确认 BIOS 文件是否选错。
5. 联系维护人员处理。

```{danger}
如果刷错 BIOS 后设备无法启动，开发者通常无法通过普通 U 盘方式自行恢复，需要专用工具或维护人员救砖。不要反复尝试刷写不确定来源的 BIOS 文件。
```
